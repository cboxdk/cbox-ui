# Cbox shell v1

One shell for every Cbox app. It covers the rail, the header with its context selectors,
the command palette, the Help column, the app switcher and the account menu. It is
rendered by cbox-ui and described by the server.

- **Status:** approved direction (Sylvester, 2026-11-10). Build not started.
- **Mockup:** https://claude.ai/artifact/9rZGjDZr5qidhhyYxJwVMx (direction only; the build must be polished, see §12).
- **Decisions this spec carries out** (Cbox Brain):
  - [URL, API and naming standard](https://app.cboxbrain.com/cbox/memories/mem_zGTv16qccSkyO6iLsQZGV8)
  - [One shared shell, React everywhere](https://app.cboxbrain.com/cbox/memories/mem_LAte7m2syNgtLhdv8myfSg)
  - [Account in rail, Help persists, ⌘K, app switcher](https://app.cboxbrain.com/cbox/memories/mem_mBjBdC2LVSHUgXvQLrQjON)
  - [Polish, search, inline create](https://app.cboxbrain.com/cbox/memories/mem_DjyhcDhdReYHYQesOpn9V9)
  - [Support portal and support updates](https://app.cboxbrain.com/cbox/memories/mem_MADDNoQrVrVAM8hWU95UE1)
  - [Shell audit](https://app.cboxbrain.com/cbox/memories/mem_8EHiQ3iCaw5ouALFnCFkWF)

## 1. Why

The audit on 2026-11-10 found these problems across the 15 apps:

- **About six different shells.** Most apps carry a copied `shared-shell.css`, which exists in four drifted versions, plus a copied `app-switcher.ts` in five versions.
- **Two shell models in cbox-ui itself** (`CboxAppShell` and `CboxWorkspaceShell`). Only Infra and Signals use either.
- **Five ways to switch organization.**
- **No working project or environment selector** in any app except Cbox ID.
- **Four words for the tenant.**
- **Support placed by hand** in 6 apps and missing in 7.

This spec replaces all of it.

## 2. Scope

**In scope**
- **cbox-ui**
  - `CboxShell` and its parts: rail, header, context selectors, command palette, Help column, app switcher, account menu, mobile sheet.
  - The `shell` prop types.
  - Removal of the old shell components.
- **laravel-console-kit:** the server side that builds the `shell` prop, plus the contracts an app implements (context, search, notifications).
- **laravel-id-client:** what the shell needs for organizations and switching.
- **laravel-assistant-client and cbox-assistant:** what the Help column and the palette need:
  - search across docs, help centre and knowledge base;
  - a page intent passed to the chat;
  - support updates;
  - the portal URL.
- **The rollout:** Cbox ID → Cbox Billing → Cbox Engage → the rest. Billing, the Assistant console and Stache move to Inertia React as part of their turn.

**Not in scope**
- Page content components such as tables and forms. They keep their current primitives; only the page header and empty state are touched where the shell needs them.
- A notifications service. The bell shows only where an app already has a source (§8).

## 3. Words

| Concept | Word in the UI | Never |
|---|---|---|
| Top-level tenant | **Organization** | Workspace, Tenant, Organisation, Account, Team |
| Second level | Named by the app: **Project** (Infra, Billing, ID), **Site** (Sites, Stache), **Space** (Brain), **Status page** (Status) | — |
| Third level | **Environment** | Plane, Stage |
| Signed-in person's settings | **Account** (menu), **Profile and security** (page) | My account, Your profile |
| Leave | **Sign out** | Log out |

Cbox ID renames its "Workspace" to Organization in its turn.

### 4.1 Rail (tier 1)

- **Size and states:** 52px wide in a 64px slot. Hovering opens it as an overlay; pinning gives 210px in a 222px slot. Inset 6px, 1px border, 12px radius. These values are kept from the design skill.
- **Top:** the service icon when collapsed. When open: the Cbox wordmark, the service name and a pin button.
- **Middle:** the app's areas from the nav registry. The active area is a filled background (`--accent-soft`), never a left-edge bar.
- **Bottom: the account button.** An avatar when collapsed; avatar, name and "Account and preferences" when open. It opens the account menu upwards (§10).
- **Pinned state** persists per person (cookie, read on the server before first paint).

### 4.2 Subnav (tier 2)

Unchanged from today's model. It appears only when an area has more than one page, collapses with ⌘. to a 26px strip, and remembers the collapsed state per person.

### 4.3 Header

- **Height:** 56px.
- **Left: context selectors** (§5).
- **Right, in this order in every app:**
  1. **Search** (⌘K): a button labelled "Search or ask…" with a `<kbd>` hint (§6).
  2. **Help:** icon plus label, with a count when there are unread support updates (§7).
  3. **Bell:** only when the app has a notification source (§8). Never rendered disabled.
  4. **Switch app:** an icon button that opens the app grid (§9).

The account is not in the header (it lives at the bottom of the rail).

### 4.4 Help column

Docked on the right from 1280px: 400px wide from 1440px, 360px between 1280 and 1439px. It pushes the page instead of covering it. Below 1280px it is a full-screen overlay (§7).

### 4.5 Mobile (below 768px), V6 (approved by Sylvester, 2026-11-11)

Replaces the 0.10 phone header (☰, a breadcrumb of every level, a nav sheet four screens long
with the account block at the bottom).

- **Top bar:** the context pill at the left (org chip; a small line with the levels above the
  deepest; the deepest large, with the environment's colour; it truncates), then Help (a dot
  while support has replied), Search, and "+" for the page's create target. No create target:
  no "+".
- **Under it:** the area's name, large; a banner tinted with the environment's colour while the
  app says the environment is not live; the area's pages as chips when there are two or more.
- **Bottom tab bar:** up to four app-declared areas (`nav.tabs`), then More.
- **More** is a full screen with push navigation and back: search all pages; the areas (each
  with its grouped pages); "Where you work" (each level opens the context sheet at that step;
  picking closes it); Help with the page; Switch app; the profile last (the account screen).
  Tapping More again goes back to its top.
- **The context sheet** has Organization and Project rows, the environment quick picks
  (current, a live one, a test one) and "All N environments", grouped by the app's groups.
  Every list has search and "New …" when the app can create.
- **Help** is a sheet "Help with {page}": ask (page and context are shared), conversations,
  articles for the page, Chat with support, Help centre. An AI answer always offers a person.
- **The palette** is a near full-screen sheet with Cancel and scope chips.
- **"+" (V7)** opens the create sheet; it never navigates away (§6.3).
- **Search fields never autofocus on touch devices.**
- **Nothing is hidden without a replacement.**

## 5. Context selectors

### 5.1 Levels

An app declares one to three levels:

| App | Level 1 | Level 2 | Level 3 |
|---|---|---|---|
| ID, Infra, Billing, Signals | Organization | Project | Environment |
| Sites, Stache | Organization | Site | Environment |
| Tax | Organization | — | Environment |
| Brain | Organization | Space | — |
| Status | Organization | Status page | — |
| Work, Engage, Telemetry, Domains, Assistant | Organization | — | — |

Telemetry's "environment" is a filter on data, not a context level. It stays a page filter.

### 5.1a Environments are app-defined (Sylvester, 2026-11-10)

"det er app afhængigt hvordan envs håndteres og tolkes. om det er sandboxe eller bare miljøer."

- **There is no fleet-wide rule** about production versus sandbox. Each app decides what its environments mean:
  - Billing and Tax have production plus sandboxes with test data.
  - In Stache and Infra every environment can serve live traffic.
- **The environment level reports per item:**
  - `name`;
  - an optional `tone` (`production`, `sandbox` or `neutral`) for the colored square;
  - an optional short `label`, e.g. "default" or "test data";
  - `testData` (boolean).
- **The app sends the items in the order it wants.** The shell does not sort them.
- **The sandbox strip** (§4.3) shows only when the current environment has `testData: true`. Its text comes from the app.

### 5.2 Triggers

- **Organization trigger:** a chip with the initials, the name and an up-down chevron (⇕).
- **Second trigger:** level 2 and level 3 share it: `[chip] Webshop · ■ Production ⇕`. An app without level 3 shows only the level 2 name. An app with level 3 but no level 2 (Tax) shows the environment in this trigger.
- **The two triggers look the same:** no border, a hover background, 32px tall, 6px radius on the chip.
- **Separator:** a light `/` between the triggers.

### 5.3 Organization menu

1. Search field. It autofocuses on desktop (fine pointer + hover), never on touch.
2. "Organizations" heading with **View all** (goes to `/orgs`).
3. Rows: initials chip, name, a check on the current one, and a gear on hover or focus (organization settings).
4. Footer: **New organization**.

### 5.4 Project and environment menu (cascade)

The menu has two panes. With no level 3 it has one pane.

**Left pane**
- Search, with the same autofocus rule.
- "{Projects}" heading with View all.
- Rows: chip, name, check, gear on hover, and a chevron ›.
- Footer: **New {project}**.

**Right pane: "Environments in {hovered project}"**
- Rows: a colored square by `tone` (production green, sandbox amber, neutral grey), the name, the app's label, and a check.
- Footer: **New environment in {project}**.

**Behaviour**
- Hovering or focusing a project shows its environments on the right without switching anything.
- Clicking an environment switches project and environment in one step.
- Clicking a project switches to it and keeps the environment with the same name, if it has one; otherwise its first environment.
- Width is about 680px. On mobile it becomes the stacked context sheet.

### 5.5 Density

Sylvester, 2026-11-10: the mockup is "klemt og flyder sammen".

- **Rows:** at least 40px tall, 12px horizontal padding, 4px between rows.
- **Lists:** 8px padding around each list.
- **Panes:** 12px padding inside each pane, and a 1px divider between panes.
- **Headings:** a section heading has 12px above it and 6px below.
- **Wrapping:** names never wrap. They truncate with an ellipsis and show the full name in a tooltip.

### 5.6 Switching semantics (one contract)

- **The URL is the state.** The organization is in the path: `/orgs/{org-slug}/…`, per the URL standard. Levels 2 and 3 are path segments the app owns, for example `/orgs/cbox/projects/webshop/environments/production/deployments`.
- **Switching stays on the same page** when that page exists in the new context.
- **Entity pages fall back.** A page showing one record falls back to that area's list, so an entity id is never carried into another context.
- **The token follows the organization.** Switching organization changes the URL. If the person's token is bound to another organization, the app re-binds it silently through laravel-id-client (`switchOrganization`, no prompt when ID has a session) and returns to the target URL. No session-only org state and no 404 on a mismatch.
- **The last used context** is remembered per person. `/` lands there.

### 5.7 Inline create

- **"New …" asks only for a name,** inline in the menu.
- **On Create** the object is created and selected, and the person lands on its details page with a "Finish setting up {name}" section.
- **The menu never blocks,** and never sends the person to another product to create something. That is the never-a-dead-end rule.

## 6. Command palette (⌘K)

- **Opening it:** ⌘K / Ctrl+K anywhere, or the header button. Esc closes it.
- **Keyboard:** ↑↓ moves through results, Enter opens one, ⌘Enter opens it in a new tab.
- **Autofocus:** desktop only.

### 6.1 Result groups, in order (V6)

Before anything is typed: **On {page}** (the page's create target and its actions), **Recent**
and **Switch** (other environments, the organization).

With a query:

1. **Actions:** the page's and the app's actions, every creatable ("New invoice"), and the switches.
2. **Go to:** organizations, and level 2/3 combinations ("Webshop · Production"), across all organizations the person belongs to.
3. **Records:** the app's search provider (§11.3), in the current context.
4. **Pages:** the nav registry, filtered by permission.
5. **Help:** docs, help centre and knowledge base, from the Cbox Assistant search API (§7.3). Opening one shows the article in Help.
6. **Ask Cbox: "{query}":** always last when there is a query. It opens Help with the question sent and the page as context.

Scope chips (All, Actions, Records, Pages, Help) keep one kind of result.

### 6.2 Behaviour

- Results come back grouped, with at most 5 per group before "Show all in {group}".
- Typing is debounced at 120ms.
- Server groups load in parallel. A slow group never blocks the fast ones.

### 6.3 Create (V7)

"+" and the palette's "New …" open the create sheet: a bottom sheet on the phone, a panel from
the right on a desktop. It opens on the page's create target (else the app's default), with
"‹ Create" up to a searchable tree of every creatable, grouped by area. A reference field
stacks the form of the thing it refers to; that form's submit says "Create and use in {parent}",
goes back and fills the field. The app declares the creatables (`shell.create`) and renders
the form bodies (`renderCreate`); cbox-ui owns the sheet, the stack and the words around them.

## 7. Help column

### 7.1 Behaviour

- **Toggles** with the Help button or `?` on a page header. The same button closes it.
- **Docked from 1280px wide** (400px from 1440px, 360px below that): the page reflows, nothing is covered. **Below 1280px it is a full-screen overlay** with a close button and Esc; its state still persists.
- **Persists across page changes and app switches,** like a browser side panel:
  - it is part of the persistent Inertia layout;
  - its open state, scroll and conversation survive navigation;
  - open/closed is stored per person.
- **Context:** an "On this page" line shows the page title and the context (`Deployments · Cbox / Webshop / Production`). It updates as the person navigates.

### 7.2 Sections, top to bottom

1. **Support updates:** shown only when there are any.
   - New replies on the person's tickets and chats, each with title, excerpt and time. Unread items are marked.
   - Opening a ticket opens it in the support portal; opening a chat opens it in the column.
   - The Help button's count is the number of unread items.
2. **Search docs and knowledge base:** one field.
3. **For this page:** up to 3 articles for the page's help topic. Each page sets `help` on its header, which is a topic key. An article opens inside the column.
4. **Ask Cbox:** the chat. It is sent the page intent (route name, page title, context) so answers are about this page. It runs only the tools this page allows, after the person confirms.
5. **Footer:**
   - **Talk to a person:** hands the chat over to support, with the conversation kept.
   - **Support portal ↗:** the dedicated portal in its own tab, also in the column header.

### 7.3 What Cbox Assistant must provide

These are new, and are built in round one:

| Need | Endpoint (on the Assistant API host) | Notes |
|---|---|---|
| Search docs, help centre, KB | `GET /v1/help/search?q=&service=&topic=` | JSON, grouped by source, permission-aware |
| Articles for a topic | `GET /v1/help/topics/{topic}/articles` | Up to 3, ordered |
| Support updates | `GET /v1/support/updates?since=` plus a broadcast channel | Unread tickets and chat replies for this person in this org |
| Mark read | `POST /v1/support/updates/{id}/read` | |
| Portal URL | in the session payload | Per org; the column hides the link when the portal is offline |
| Page intent | `support.js` sends `intent` (route, title, context) when the session starts and on navigation | The widget API already accepts `intent` |

`laravel-assistant-client` wraps these. The app only registers its service key and help topics; the shell does the rest.

## 8. Notifications bell

- **When it shows:** only when the app registers a notification source in console-kit (unread count, latest items, mark read). Without one, the bell is not rendered at all; there is no disabled bell.
- **What it holds:** product events. Support replies belong to Help (§7.2), not the bell.

## 9. App switcher

### 9.1 Shape

- **Panel:** about 440px wide, a 3-column grid, Google-launcher sized.
- **Tile:** a 48px app icon in the app's fixed hue (light and dark variants), the app name, and a one-line purpose ("Identity and sign-in").

### 9.2 Sections

- **In {organization}:** the apps the organization has. The current app is marked.
- **More from Cbox:** the apps it does not have yet, dimmed. They open that app's admission/signup page in the same organization.
- **Footer:** "All products ↗".

### 9.3 Data

- **Source:** the existing catalog endpoint from laravel-id-client (`CboxId::appCatalogRoutes()`).
- **Gaps to close:** the catalog must also return apps the organization does not have (with `admission_url`), plus `purpose` and `hue`.
- **No pin favourites in v1.**

## 10. Account menu (from the rail)

1. Header with name and "Signed in with Cbox ID".
2. Profile and security: goes to Cbox ID.
3. Language, Regional format and time zone. These are the shared preferences in Cbox ID's `preferences` contract.
4. Theme: System / Light / Dark, a segmented control.
5. Switch account.
6. Sign out.

## 11. Data contract

### 11.1 The `shell` prop

Every app shares one Inertia prop, `shell`. cbox-ui exports its TypeScript type, and console-kit produces it. Shape (abridged):

```ts
type Shell = {
  app: { key: AppKey; name: string; homeUrl: string };
  person: { id: string; name: string; initials: string; avatarUrl?: string };
  nav: { areas: NavArea[]; activeArea: string; activePage?: string };
  context: {
    levels: ContextLevel[];       // 1–3, in order
    switchUrl: string;            // POST target; server resolves same-page or list fallback
  };
  palette: { searchUrl: string; actions: PaletteAction[] };
  help: { enabled: boolean; topic?: string; sessionUrl?: string; portalUrl?: string; updatesUrl?: string };
  notifications: { enabled: false } | { enabled: true; unread: number; url: string };
  apps: { catalogUrl: string };
  banner?: { kind: 'sandbox' | 'impersonation' | 'notice'; text: string; action?: Link };
  preferences: { theme: 'system' | 'light' | 'dark'; locale: string; railPinned: boolean; helpOpen: boolean };
};

type ContextLevel = {
  key: 'organization' | 'project' | 'environment' | string;
  label: string;                  // "Organization", "Site", "Space"…
  current: { id: string; name: string; initials?: string; tone?: 'production' | 'sandbox' | 'neutral'; label?: string; testData?: boolean };
  listUrl: string;                // lazy JSON, searchable: ?q=&parent=
  createUrl?: string;             // POST {name} → {id, detailsUrl}
  allUrl: string;                 // "View all"
  settingsUrl: (id: string) => string; // rendered as a URL template on the wire
};
```

### 11.2 Lists load lazily

The prop carries only the current selection. The menus fetch `listUrl`, which is paginated and searchable, when they open, so an org with 400 projects never bloats every page.

### 11.2a Local first

This follows the policy that every service renders from local data
([mem_5Wiv6CAyGpwL0E3nJC6S8q](https://app.cboxbrain.com/cbox/memories/mem_5Wiv6CAyGpwL0E3nJC6S8q)).

- **No synchronous calls to another service** when building `shell` or answering `listUrl`. Organizations come from the app's local mirror of Cbox ID, and the app catalog comes from a cached copy.
- **Help, support updates and docs search** load in the browser, after the page has painted.
- **If Assistant or ID is down,** the shell still renders. Help shows that it is unavailable, and the menus work from local data.

### 11.3 What an app implements (console-kit)

```php
Console::shell()
    ->levels(new OrganizationLevel(), new ProjectLevel(), new EnvironmentLevel())  // ContextLevel contract
    ->search(new DeploymentSearch())                                                // SearchProvider contract
    ->actions(fn () => [PaletteAction::route('deployments.create', 'New deployment')])
    ->helpTopic(fn (Request $r) => $r->route()?->getName())
    ->notifications(null);                                                          // or a NotificationSource
```

console-kit ships the following:
- `OrganizationLevel` on top of laravel-id-client: the person's organizations, switching and creation.
- The `HandleShell` middleware, which shares `shell`.
- The switch endpoint, with the same-page / list-fallback resolution.
- Fakes for tests.

## 12. Quality bar

The shell is not done until all of these hold.

### 12.1 Polish
- Every scroll container scrolls on its own and smoothly: page, subnav, menus, panes, palette, Help.
- Nothing jumps when a menu opens.
- No layout shift on first paint. Theme, rail pin and Help open are applied before paint.
- Alignment and spacing follow the tokens. The §5.5 density holds.
- Light and dark are both pixel-checked.

### 12.2 Keyboard and accessibility
- All menus are ARIA menus or listboxes with roving focus.
- ↑↓ Home End Enter Esc work; Tab leaves a menu.
- Focus returns to the trigger on close.
- Visible focus rings everywhere.
- Text contrast is at least 4.5:1.
- Targets are at least 32px on desktop and 44px on touch.
- Help and the sheets trap focus only when they are modal (mobile).

### 12.3 Tests
- **Unit tests (vitest + Testing Library)** for every part:
  - switching semantics;
  - cascade hover;
  - inline create → details;
  - autofocus only with a fine pointer;
  - the bell absent without a source;
  - Help persisting across a simulated Inertia visit.
- **Playwright visual snapshots:** desktop 1440 and mobile 390, light and dark, for each open state (org menu, cascade, palette, Help with updates, app switcher, account menu, sandbox strip).
- **console-kit:** Pest tests for the payload, the switch endpoint and the fakes.
- **No app adopts the shell until all of the above are green.**

## 13. What is removed from cbox-ui

- **Components:** `CboxAppShell`, `CboxAppSidebar`, `CboxWorkspaceShell`, `TopBar`, `OrgSwitcher`, `CboxOrgContextBar`, `AppLauncher`, `AppSwitcher` (React), `UserMenu`, `SearchTrigger`, `NotificationsBell`, `CboxMobileNavDrawer`, `ContextBar`.
- **Surface stubs:** `search`, `activity` and `help`. They are replaced by the palette and the Help column; `inbox` stays if an app uses it.
- **Elements:** `<cbox-app-switcher>` stays only as long as an app still needs it during migration.
- **Version:** `@cboxdk/cbox-ui` 0.10.0 is a breaking minor under the 0.x caret rules (see the `cbox-release` skill).

In each app, its copied `shared-shell.css`, `app-switcher.ts`, `Shell.tsx`, `service-marks.json` and `chrome/*` are deleted in its turn.
